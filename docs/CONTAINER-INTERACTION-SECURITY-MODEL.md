# Container Interaction and Security Model

Mainstay uses several kinds of communication inside one deployment. They are
deliberately different. Treating them as one generic network surface would make
operator-only capabilities easier to expose by accident.

This note defines the current interaction pattern and the security rules that
must hold as `mainstayctl`, Safebox Web, Clear, Grove, Spurline, and future
services become more capable.

## Three Context Lanes

### Shared Local Context

Shared local context is state that exists only inside one Mainstay instance.
It is normally carried by Docker volumes, bind mounts, environment variables,
or local files.

Examples:

- `mainstay-local` reading the Safebox claimed-handle database through a
  read-only mount;
- Safebox Web and `service-acorn-worker` sharing a reserve snapshot file;
- Safebox Web queueing a service-Acorn reserve funding request for the worker;
- installation secrets generated by `init-env.sh` and stored in the instance
  `.env`.

This lane is fast and practical because the containers are co-resident. It is
not a protocol surface. Data in this lane must not be copied into public
metadata unless it has first been reduced to a safe, intentional claim.

Security rules:

- mount shared state read-only unless the caller must write it;
- keep private keys, wallet recovery state, bearer proofs, and operator tokens
  out of diagnostic snapshots;
- make request files narrow and typed, such as amount, mint, status, invoice,
  and confirmation result;
- use one wallet owner for mutable wallet state; other containers request work
  rather than opening the same wallet directly;
- preserve file permissions suitable for secrets or operator state.

### Container-to-Container Management Context

Container-to-container management is internal service control over the private
runtime network. It is used when an admin surface needs a live service answer
but should not require Docker access inside the admin container.

Examples:

- `mainstayctl reserve balance` calling Safebox Web at
  `http://safebox-web:8000/internal/service-acorn/reserve`;
- `mainstayctl reserve fund <amount>` asking Safebox Web to queue a
  service-Acorn reserve funding request;
- future narrow internal status, commissioning, or maintenance endpoints.

This lane is operator control, not user protocol. It must remain private to the
instance and authenticated even though it runs on the Docker network.

Security rules:

- require `SAFEBOX_MANAGEMENT_TOKEN` or an equivalent deployment-local
  management credential;
- return `404` when the management credential is not configured so the endpoint
  is not accidentally advertised as a public feature;
- keep responses limited to safe operational fields;
- avoid exposing private keys, recovery phrases, bearer proofs, unsigned
  blanket authority, or arbitrary command execution;
- prefer explicit allowlisted endpoints such as `/internal/service-acorn/...`
  over generic proxy, shell, or file-access endpoints;
- do not publish internal management paths through a reverse proxy;
- if a service is exposed externally, deny `/internal/` paths at the proxy and
  keep container firewalls or network policy as a second boundary where
  available.

### External Protocol Context

External protocol context is communication that intentionally crosses the
Mainstay instance boundary. It must be safe when reached from another machine,
another operator, another address space, or a future FIPS route.

Examples:

- Clear token transfer through a recipient's advertised relay;
- NIP-05 lookup and Nostr relay discovery;
- externally reachable Clear mint, Grove, or Lightning routes;
- signed treasury functions from an authorized treasurer `npub`;
- future FIPS paths that carry the same identity and authority model over a
  different transport.

This lane must not rely on Docker-local trust. It should carry its own identity,
authorization, replay protection, and reachability checks.

Security rules:

- require signed protocol messages for remote treasury or authority-bearing
  functions;
- separate mint operator authority from currency or treasurer authority;
- bind claims to stable identifiers such as service `npub`s, wallet `npub`s,
  Clear keyset IDs, and content hashes rather than to one URL;
- treat URLs, DNS names, relay addresses, and FIPS locators as routes, not as
  the authority itself;
- fail closed when an internal-only route is offered to an external recipient.

## Boundary Summary

| Lane | Boundary | Typical mechanism | Authority model |
| --- | --- | --- | --- |
| Shared local context | One instance | Volume, file, env var | Deployment-local operator context |
| Container management | One instance network | Internal HTTP plus token | Operator/admin control |
| External protocol | Beyond instance | Nostr, HTTPS, Clear, Lightning, FIPS | Signed portable protocol authority |

The main safety invariant is:

> Operator authority stays local or internal. Protocol authority is signed,
> portable, and independent of the local deployment.

## Current Applications of the Pattern

### Service-Acorn Reserve

The service Acorn wallet is owned by `service-acorn-worker`. Safebox Web does
not open that wallet to fund the reserve. Instead:

1. `mainstayctl` calls an authenticated internal Safebox Web endpoint.
2. Safebox Web writes a narrow reserve-funding request into shared local state.
3. The worker, which already owns the wallet, creates the invoice and checks
   settlement.
4. Safebox Web exposes safe status fields to `mainstayctl`.

This avoids putting Docker access in `mainstay-local` and avoids multiple
containers mutating the service Acorn wallet at the same time.

### Local Clear Send

`mainstayctl clear send` is an operator convenience wrapper for the managed
instance. It resolves a bare local handle using local Safebox context, uses the
internal Clear and Spurline routes, and deliberately permits internal-mint
delivery only for same-instance recipients.

It is not a general external Clear send protocol. External Clear transfers must
use externally reachable mint and relay routes and must respect the recipient's
advertised capabilities.

### Clear Root Operator and Treasurer Functions

The Clear root operator authority is a service/operator authority. It exists so
the mint can be commissioned, tested, and administered. It is distinct from a
currency authority.

A treasurer is responsible for issuance policy, liability, redemption, and
other currency-specific rules. Remote treasury functions should therefore be
authorized by signed envelopes from the treasurer `npub`, not by possession of
a Docker-local operator token.

## Security Review Checklist

Before adding a new cross-container or external capability, answer these
questions:

1. Which lane does this action belong to: shared local, container management,
   or external protocol?
2. Is the endpoint accidentally reachable through a host port or reverse proxy?
3. If the action is operator-only, is it protected by a deployment-local
   management credential and unavailable when that credential is missing?
4. If the action is remote or treasury-related, is it authorized by a signed
   protocol envelope from the correct `npub`?
5. Does the response omit private keys, recovery material, bearer proofs, and
   broad operator tokens?
6. Does the design preserve a single owner for mutable wallet or database
   state?
7. Does it fail closed when an internal route is unavailable instead of
   silently switching to an external route?
8. Does any public advertisement use stable identities and safe reachable
   routes rather than Docker-only URLs?

## Reverse Proxy Guidance

Publishing a service through a reverse proxy changes its reachability scope. A
proxy configuration must not expose internal management routes.

Minimum rule:

```text
deny /internal/
```

Equivalent rules should be applied before any catch-all proxy rule. The
application should still require a management token because proxy rules are a
deployment boundary, not the only security boundary.

For Clear, do not expose operator routes such as `/v1/operator` on the public
mint service. Public mint APIs and privileged operator APIs should remain
separate services or be separated by network policy and explicit path blocking.

## Relationship to Invariant Identity

This model mirrors Mainstay's identity and reachability model. An `npub`, Clear
keyset ID, Grove content hash, or service identity can remain stable while the
route changes from internal Docker DNS to LAN, public HTTPS, VPN, or FIPS.

The route is context. The identifier is durable. Authority must be bound to the
durable identifier and the correct role, not merely to the path that happened
to carry the request.

## Non-Goals

This note does not make every internal endpoint safe for public exposure. It
does not replace formal protocol authorization for treasury functions. It does
not make Docker network privacy a sufficient security control by itself.

The goal is a clear default: internal operator convenience can improve
deployment ergonomics while remaining separate from externally trusted
protocols.
